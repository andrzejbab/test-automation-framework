############ pytest doc ##################
Standard Python requests (End-to-End Testing)
Use standard Pytest with requests (without Schemathesis) for sequential,
stateful business logic.

Why: You need absolute control over the order of operations, variables, 
and external dependencies (like Mailpit or databases).
Use cases: Password resets, user registration flows, checkout carts, or any A -> B -> C process.


conftest.py 
     Fixtures defined in conftest.py are automatically discovered and can 
     be used in any test file within the same directory or its subdirectories

pytest.ini
     file is used to configure pytest’s behavior for your test suite. 
     It allows you to set options such as:
        1. Default command-line options (e.g., addopts for flags you always want to use)
        2. Test discovery rules (e.g., testpaths, python_files, python_classes, python_functions)
        3. Registering custom markers (to avoid warnings and document marker usage)
        4. Configuring plugins and their options
        5. Setting log levels, output formats, and other test environment settings

How to test grouping:
    1. Directory-based grouping by domain/layer (e.g., api, ui, tests/db/, tests/services/),
       with files per feature (test_user_management.py, test_messages.py).
    2. Markers for intent so you can slice runs: smoke, regression, slow, db, api, ui, selenium, integration, e2e.
        Runs like pytest -m "smoke and not slow" are standard.
        Run subsets: pytest -m mock or pytest -m "integration and not mock".
    3. Test classes per feature/behavior inside files for organization and shared fixtures, without overusing inheritance.
    4. Parametrization with ids for matrixed cases while keeping counts low per test for readability.
    5. Fixture scopes for setup cost control (session/module for expensive setup)

#### Fixture vs helper functions (When to use) #####
-> We use fixtures to safely manage side effects because Pytest has built-in mechanisms (like yield)
-> We write helper functions to be completely free of side effects. If your assert_response helper secretly 
updated a database record or changed a global configuration while verifying the status code, 
it would cause unpredictable bugs in subsequent tests that are incredibly hard to track down.
to clean up those changes after the test finishes.

Fixtures are built for Arrange and Cleanup (setup and teardown), while helper functions belong in the Act and Assert phases.

Quick Rules of Thumb
    -> Use a Fixture if you find yourself asking: "What does my test need in place BEFORE it can execute?"
    -> Use a Helper Function if you find yourself asking: "How do I process or verify what my test produced AFTER it ran?"

####  Fixtures ####
Check available fixtures:
    python -m pytest --fixtures

Verify fixtures:
    python -m tests.fixtures.user_fixtures

Pytest Fixture scopes:
    "function": The fixture is created and destroyed for each test function (default).
    "class": The fixture is created once per test class.
    "module": The fixture is created once per test module (file).
    "session": The fixture is created once for the entire test session (all tests).

####### yield in fixture ####
In Pytest fixtures, exactly one yield execution is allowed per test run to establish a clean
Setup -> Test -> Teardown lifecycle.
1. Before yield (Setup): Code runs before the test (It prepares the environment, seeds database records, or instantiates API clients)
2. At yield <value>: Pauses the fixture and passes the yielded value into the test function. Pytest hands over control so 
    the test can execute its Act and Assert phases.
3. After yield (Teardown): Code resumes automatically after the test finishes—even if the test failed or threw an exception—to
    close database connections, delete temporary files, or revoke tokens.

    @pytest.fixture
    def temporary_database_record():
        # 1. SETUP: Create record
        record = Record.objects.create(name="test_item")
        
        # 2. HANDOFF: Send object to test method
        yield record 
        
        # 3. TEARDOWN: Clean up state after test completes
        record.delete()

####  Examples of using pytest fixtures: #####

1. As a function argument:

    import pytest

    @pytest.fixture
    def sample_data():
        return [1, 2, 3]

    def test_sum(sample_data):
        assert sum(sample_data) == 6

2. As a dependency in another fixture:

    @pytest.fixture
    def base():
        return 10

    @pytest.fixture
    def double_base(base):
        return base * 2

    def test_double(double_base):
        assert double_base == 20

3. Using pytest.mark.usefixtures:

    import pytest

    @pytest.fixture
    def setup_env():
        print("Setup environment")

    @pytest.mark.usefixtures("setup_env")
    def test_env():
        assert True

4. In a test class:

    import pytest

    @pytest.fixture
    def user():
        return {"name": "Alice"}

    class TestUser:
        def test_name(self, user):
            assert user["name"] == "Alice"

#### Mocking/Stubing  -> standard in pytest #######
Stubbing: 
    Setting a predefined return value or side effect (return_value=...) to control test data flow.

Mocking:
    Verifying interaction history after execution (assert_called_once_with(...)).

    ### Rest Api test specific ######
    requests_mock.Mocker()
        is a context manager (or decorator) that patches the entire requests API
        for the duration of the block/fixture. Inside, every requests.get/post/patch/... call is intercepted,
        and you register expected URLs/responses on the provided mocker instance (m).
        When the block exits, patching is undone automatically.
    requests_mock
        is the dedicated library for HTTP mocking of requests; 
        it understands URLs, methods, query params, and can assert call counts/ordering.
        It works at the HTTP layer, not by monkey‑patching your own functions.

        Examples:
        def test_for_mocker(self, requests_mock):
            requests_mock.post("http://localhost:8000/api/user_management/token/",
                            json={"access": "mock-access", "refresh": "mock-refresh"},
                            status_code=200)
            resp = requests.post("http://localhost:8000/api/user_management/token/",
                                json={"username": "test", "password": "test"})
            assert resp.status_code == 200
            assert resp.json() == {"access": "mock-access", "refresh": "mock-refresh"}

        #Context manager
        def test_single_call():
            with requests_mock.Mocker() as m:
                m.get("https://api.example.com/ping", json={"pong": True}, status_code=200)

                resp = requests.get("https://api.example.com/ping")
                assert resp.status_code == 200
                assert resp.json() == {"pong": True}
        

    ## mocker / monkeypatch fixtures ###########
    
    ## Fixture mocker ###
    mocker.patch() / mocker.patch.object() 
        come from pytest-mock (a thin wrapper around unittest.mock). 
        They replace Python attributes/functions you point at (e.g., a function, method, or attribute), not the HTTP layer.
        You’d use these to stub your own code paths, not to simulate HTTP responses.

    Example:
        1. Use mocker.patch when you want to target where a function or class is imported and used.
        String path where the target is used:
            # Stubbing: Force my_module.send_email to return fake data
                mocker.patch("my_module.send_email", return_value=True) replaces that function during the test.
            # Patching and saving the mock reference
                mock_send = mocker.patch("my_app.email_service.send")
                # Behavior verification
                mock_send.assert_called_once_with(email="bob@example.com", template="welcome")

        2. Use mocker.patch.object when you already have access to the class or instance in your test file. 
        This is safer against typos because your IDE can auto-complete object attributes.        
        Object reference + attribute name
            # --- STUBBING with mocker.patch.object ---
                replaces a specific attribute/method on an object.
                mocker.patch.object(obj, "attr", ...) 
                mocker.patch.object(PaymentProcessor, "charge", return_value={"success": True}
            # --- MOCKING with mocker.patch.object ---
            mock_charge = mocker.patch.object(PaymentProcessor, "charge")
                # Behavior verification
                mock_charge.assert_called_once_with(100)
                
    ## Fixture monkeypatch (Pytest Native Stubbing) ###
    monkeypatch is built into pytest (no plugins required). 
    It replaces attributes with whatever you pass in, making it a pure stubbing tool.
    Key Takeaway: monkeypatch is basically a safe "swap" tool. It doesn't care 
        what it is swapping. You can hand it a function, a lambda, a class, a string, 
        or a custom object, and it will temporarily inject it into your module for 
        the duration of the test.
    Examples: 
        # Stubbing Environment Variables
        # Set a fake environment variable (safely isolated to this test)
            monkeypatch.setenv("SECRET_API_KEY", "test_key_999")
        # Replace the 'Database' class in my_module with our DummyDatabase
            monkeypatch.setattr(my_module, "Database", DummyDatabase)
        # Target JUST the fetch_avatar method on the UserProfile class
            monkeypatch.setattr(user_profile.UserProfile, "fetch_avatar", lambda self: "http://fake.com/pic.jpg"
        # Swap out the entire 'settings' object with our FakeSettings instance
            monkeypatch.setattr(app_config, "settings", FakeSettings())
        # Insert a fake object/value into the dictionary
            monkeypatch.setitem(app_state.active_sessions, "token_123", {"role": "admin"})

    Rule of Thumb:
        1. Use monkeypatch for quick stubbing of environment variables, dictionaries, or simple 
        return values when you don't need unittest.mock assertions.

        2. Use mocker.patch.object() whenever you can import the class/module 
        directly in your test (safest for refactoring).

        3. Use mocker.patch() with string paths when patching third-party 
        library imports inside the module under test.

    Using monkeypatch and mocker together in the same test is a very common pattern.
    You typically use monkeypatch to set up the environment or internal state (the stub), 
    and mocker to track interactions with external systems (the mock).


#### Mocking/Stubing  -> HTTP requests #######
    request is a built-in pytest tool used for managing your tests, while responses is an
    external library used for mocking HTTP network calls.

    The community standard is to use a library like responses (or requests-mock),
    which intercepts the HTTP requests at the socket level.

    request -> Lets your fixtures see information about the test that is currently running.
        Primary Use Case:
            Parameterizing fixtures, reading test markers, or running setup/teardown code.
        Examples:
            # We pass 'request' into the fixture to access the parameters
            @pytest.fixture(params=["user@example.com", "admin@example.com"])
            def user_email(request):
                # request.param holds the current value for this test run
                return request.param

            # This test will automatically run TWICE, once for each email
            def test_email_format(user_email):
                assert "@" in user_email
            
            @pytest.fixture
                def print_test_name(request):
                    print(f"\nCurrently running: {request.node.name}")

    responses -> Intercepts HTTP network calls made by the requests library and returns fake data.
        Primary Use Case:
            Mocking/stubbing third-party APIs (like weather services, payment gateways).
        Example: @responses.activate
            def test_external_api():
                # 1. Setup the fake network response
                responses.add(
                    method=responses.GET,
                    url="http://fake-api.com/data",
                    json={"status": "success"},
                    status=200
                )

                # 2. Application code uses the standard 'requests' library
                # The 'responses' library intercepts this call secretly!
                res = requests.get("http://fake-api.com/data")
                
                assert res.json()["status"] == "success"



    How to start from VS Code terminal (with mocks) with CLI options:
        Run the class only:
